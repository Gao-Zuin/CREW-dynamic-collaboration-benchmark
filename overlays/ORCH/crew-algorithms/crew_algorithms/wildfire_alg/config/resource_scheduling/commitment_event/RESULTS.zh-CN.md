# DeepSeek Flash 单例运行：新增五名平民，再出现邻近火点

配置：`FiveCiviliansAt80_75AfterOriginalFireDozerMovesThenFireAt80_80_WorkerReport`，seed 42，动态组织，26 步，11 名 worker。请求模型名为 `deepseek-v4-flash`，API 响应名为 `deepseek-flash`。worker 和组织者调用都关闭思考输出；同一步 worker 模型调用并行，消息下一步投递。2026-11-10 运行，日志在本机 `benchmark_runs/commitment_event_deepseek_v4_flash_corrected_seed42_20261110/`，可复核的摘要见同目录的 `deepseek_v4_flash_seed42_adaptive_result.json`。

| 事实 | 新平民 `(80,75)` | 新火点 `(80,80)` |
|---|---:|---:|
| 提交事件 | 第 8 步，`condition_met` | 第 14 步，距前事件 6 步 |
| 官方坐标先送到 | 消防员 2 | 无人机 10 |
| worker 带坐标报告组长 | 第 10 步 | 第 16 步 |
| 组长带坐标报告组织者 | 未发生 | 未发生 |
| 新鲜局部视野目击目标 | 未发生 | 未发生 |
| 释放时最近的对应执行者理想移动下界 | 消防员 2 步 | 消防员 3 步、无人机 3 步 |

第 0 步原火组的推土机发生位移，第 1 步执行清树动作，环境累计清树数由 0 增至 16；第 8 步原火活跃、初始获救人数为 0，因此首事件确实按状态触发。触发器本身只要求位移，清树由轨迹另行核实。组织者共提交 9 次成员图，其中第 14 步与第 15 步发生事件后的成员变化，但两次新事件的坐标均未由组长上报组织者，不能把这些变化归因于新事件。worker 的报告明确要求组长通知组织者；组织者后续仍主要处理原火 `(22,50)` 一带。这个实例展示了**信息已到组长，却未落实到中心决策**的失败点。

第 25 步终局：全局获救人数 0 / 10，火势仍活跃，灭火数 0，累计清树 133，毁损 agent 1，整体任务失败。新增平民实体数、新增平民获救数和新火点分区扑灭情况不能由现有全局奖励独立确定，摘要保留为空值。最近职业的移动下界仅证明接近目标有时间余地，不证明完整救援与扑火可行；仍需成功的参考调度轨迹。

资源开销：1128 次 API 调用，输入 3,860,911 token，输出 227,532 token。8 次组织者响应中 1 次因成员约束被拒，其余提案可解析。此前一条同任务轨迹因组织者调用未关闭思考输出，33 次响应中 31 次达到 4096 token 上限并解析失败；它只用于定位配置错误，不作为模型协作能力结论。该轨迹第 15 步曾在来源限定的局部视野中出现新火格和平民格，支持事件注入确有物理效果，但不能证明实体数或救援完成。

下一步最有价值的验证：从相同第 8 步状态分别运行“组长强制转发新事件”和原协议，保持模型与后续调度器一致，隔离信息传递失败的影响。随后补独立实体 ID 与分区火势计数，并以一条成功的脚本调度轨迹验证完整物理可行性。
